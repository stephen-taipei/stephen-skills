# 候選判定準則

用來判斷一段 JS/TS 邏輯**是否值得**搬到 Rust/WASM。先看反指標（快速排除），再看正面指標（確認值得）。

---

## 反指標 —— 命中任一條就排除

排除比納入重要。WASM 不是萬用加速器，硬做會付出可觀的複雜度成本卻換不到效益。

### 1. 單次執行時間太短

單次 < 1ms 的函式直接排除，即使呼叫很頻繁。

JS ↔ WASM 的跨界呼叫本身有固定開銷（數十微秒到數百微秒，視資料量與型別而定）。單次工作量小於這個量級時，搬過去只會更慢。

> 例外：如果能把「呼叫 10000 次、每次 0.1ms」重構成「呼叫 1 次、處理 10000 筆」，那就不是這條反指標，而是**批次化後的好候選**。判斷時要看得出這個可能性。

### 2. 瓶頸不在 CPU

先確認慢的原因。以下都與 WASM 無關：

| 真正的瓶頸 | 徵狀 | 該往哪裡解 |
|-----------|------|-----------|
| 網路 / API 等待 | Performance 面板大片 idle，時間花在 waiting | 快取、預取、併發、後端 |
| DOM 操作 / 重排重繪 | Layout、Recalculate Style、Paint 佔大宗 | 虛擬列表、批次更新、CSS containment |
| 框架 re-render | 大量 component update | memo、訂閱粒度、狀態結構 |
| 主執行緒被其他工作卡住 | 你的函式其實很快 | 先找真正的長工作 |

**沒有 profile 過就不要假設瓶頸在計算。**

### 3. 大量字串且需頻繁跨界

字串跨 JS/WASM 邊界要做 UTF-8 編解碼與記憶體複製，成本高。

- ❌ 每次呼叫傳入/傳出字串、呼叫成千上萬次 → 排除
- ⭕ 一次傳入整份大文字、在 Rust 內部處理完一次回傳 → 可考慮

### 4. 重度依賴 JS 生態或瀏覽器 API

邏輯裡大量用到 DOM、Canvas API、`fetch`、第三方 JS 套件時，搬到 Rust 得靠 `wasm-bindgen` 回呼 JS，每次回呼都是跨界成本，通常得不償失。

可行的做法是**縮小範圍**：只把中間那段純計算抽出來，I/O 與 API 留在 JS。若抽不出純計算核心，排除。

### 5. 資料總量太小

即使演算法複雜度高，n 很小的時候常數項才是主導。陣列長度 < 1000 且無巢狀迴圈時，通常不值得。

### 6. 程式碼正在頻繁改動

正在迭代中的業務邏輯搬到 Rust 會讓改動成本倍增（改 Rust → 重編 → 重測）。等穩定下來再說。

## 正面指標 —— 符合越多越值得

### 強訊號

| 指標 | 說明 | 判斷方式 |
|------|------|---------|
| **單次 > 50ms** | 已構成 long task，直接阻塞主執行緒 | Performance 面板 / `performance.now()` |
| **純計算、無副作用** | 輸入輸出明確，不碰 DOM/網路 | 讀原始碼 |
| **資料可用 TypedArray 表達** | 數值陣列、像素、音訊取樣、二進位 | 看資料型別 |
| **演算法明確且穩定** | 規格清楚、不常改 | 看 git 歷史 |
| **熱路徑高頻呼叫** | 捲動、輸入、動畫中被反覆觸發 | 呼叫點分析 |

### 典型適合的工作型態

- **影像處理** —— 濾鏡、縮放、色彩空間轉換、像素級運算（`ImageData` 直接就是 `Uint8ClampedArray`）
- **音訊處理** —— FFT、重取樣、編解碼
- **加解密 / 雜湊** —— 大量資料的 hash、簽章、對稱加解密
- **壓縮 / 解壓** —— 自訂格式的編解碼
- **大陣列數值運算** —— 矩陣、幾何、統計、訊號處理
- **diff / patch** —— 大型結構或文字的差異比對
- **parser / tokenizer** —— 自訂 DSL、大型格式解析
- **路徑搜尋 / 圖論** —— A*、最短路徑、拓撲排序
- **大量排序與聚合** —— 十萬筆以上的多鍵排序、分組統計

### 加分條件

- 該邏輯**已經有測試** → 等價性驗證成本低
- 該邏輯**已被隔離成純函式** → 替換介面單純
- 專案**已有 wasm 或 Worker 基礎建設** → 整合成本低

## 掃描手法

### 1. 靜態前篩

`scripts/scan-candidates.mjs` 會標記這些模式：

- 巢狀迴圈（`for`/`while` 內再有 `for`/`while`）
- 大陣列操作鏈（`.map().filter().reduce()`、`.sort()`）
- TypedArray 使用（`Uint8Array`、`Float32Array`、`ImageData`…）
- 像素級 API（`getImageData`、`putImageData`、`createImageData`）
- 計算關鍵字（`hash`、`encrypt`、`compress`、`matrix`、`fft`、`distance`、`interpolate`、`tokenize`、`parse`…）

**這只是前篩。** 它讀不出資料規模，也讀不出實際耗時 —— 兩者都要你自己判斷。

### 2. 依賴掃描

檢查 `package.json` 中 CPU 密集的套件，它們常常標示著計算熱點所在：

`crypto-js`、`bcryptjs`、`fuse.js`、`pdfjs-dist`、`jszip`、`xlsx`、`sharp`(node)、`d3-*`、`turf`、`ml-*`、`tesseract.js`

### 3. 實測（最可靠，有條件就做）

有 Chrome DevTools MCP 或 Playwright 時：

1. 載入目標頁面，觸發目標操作
2. 錄 performance trace
3. 找出 long task（> 50ms）與其呼叫堆疊
4. 記錄目標函式的實際 self time 與呼叫次數

**實測得到的候選，可信度遠高於靜態掃描。** 有實測就在清單標 `實測`。

---

## 判定流程

```
候選項目
   │
   ├─ 命中任一反指標？ ── 是 ──▶ 排除（記錄原因，寫進「已排除」表）
   │
   └─ 否
      │
      ├─ 有幾個強訊號？ ── 0 個 ──▶ 排除（效益不明顯）
      │
      └─ ≥ 1 個
         │
         └─ 能實測嗎？ ── 能 ──▶ 實測後標 `實測`，列入建議
                          └─ 不能 ──▶ 標 `估算`，列入建議並註明未驗證
```
